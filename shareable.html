TRex as a Versioned Parent Framework

A proposal for distributing, versioning, and upgrading the framework and its generative assets — grounded in how hypershell consumes TRex today.

Document: Architecture proposal · Status: Draft for review · Date: 2026-10-12

Scope: TRex repo strategy only — no code changes proposed in this pass.

Reference consumer: openshift-online/hypershell (live). The previous consumer, agent-control-plane, is retired; it appears here only as a cautionary precedent of the copy-fork failure mode.

Review process: This document carries two independent reviews. Review 1 is written in the persona of a strict Senior Distinguished Architect. Review 2 is written by a fresh reviewer, seeded with the School of the Pragmatic Programmer, who both re-reviews the solution and explicitly validates or rejects each finding of Review 1.

1 · Executive summary

TRex's stated intent is to be a versioned parent library and code generator that absorbs the accidental complexity of a modern Go REST/gRPC control plane, leaving child projects only their essential complexity. That intent is currently structurally blocked: the module refactor in PR #45 (2026-09-10) removed the root Go module, and no release since has been resolvable by any consumer through any path. The live child, hypershell, has responded by hand-building an entire distribution layer around the gap — commit-ref pin files, cached checkouts, vendored generator forks, drift-detection make targets, and a forked skills tree.

This proposal's thesis is simple: everything hypershell built by hand is the requirements list. The right architecture productizes their workarounds into TRex itself, so the next child never rebuilds them:

  1. One versioned root module containing the framework and every generator, so a single tag resolves everything a child consumes (§4.1).
  2. A checkout-free generator CLI, trex-gen, installed at a pinned version with templates embedded (§4.2).
  3. A two-class ownership model for generated code — mechanical files that upgrade freely, scaffold-once files the child owns — enforced by a manifest and hash-based conflict detection, with a real upgrade command (§4.3).
  4. Defined customization seams and a recorded template-override protocol, so children extend rather than fork (§4.4).
  5. Versioned skill distribution with TRex-owned vs child-owned file markers (§4.6).

Section 3 states twelve testable requirements; Section 4 details the solution; Sections 5–6 present and defend alternatives; Section 7 phases the migration so hypershell can adopt at leisure; Sections 8–9 subject the whole proposal to two adversarial reviews.

2 · Field evidence — how hypershell consumes TRex today

Hypershell is a multi-component monorepo (api-server, control-plane, cli, sdk-go, sdk-typescript, web-console, fleet-dashboard, agents) whose API server is built on TRex with 16 kind and cross-cutting plugins. Nothing below is hypothetical — every row was verified in the hypershell working tree.

2.2 Observed failure modes

  • Version skew inside one child. components/api-server pins pseudo-version v0.0.0-20261010200958-071bd1d… (current tip) while components/cli pins v0.0.0-20261007150231-ff48c56… (three days older) and rh-trex-ai.ref sits at ff48c56. Three pins, two versions, reconciled by hand.
  • Unresolvable releases. TRex tags v0.0.32–v0.0.35 were cut after the module move; none carries a root go.mod, so the root path cannot resolve them, and none carries components/api-server/vX.Y.Z nested tags, so the nested path cannot either. The last tag resolvable by any path was v0.0.31 (2026-07-06) — on the now-dead root path.
  • A broken scaffold. templates/new-project/ requires the nonexistent root module, imports rh-trex-ai/pkg/cmd paths that resolve nowhere, and its README claims it "includes the TRex.AI Kind generator" while shipping no scripts/ or templates/ directory at all.
  • The copy-fork precedent. The retired consumer (agent-control-plane) forked the generator, the templates, and the skills tree wholesale, then froze at v0.0.31 — the last tag its import path could resolve. That is where every copy-fork consumer ends.
Read together: hypershell has already paid the full price of TRex's missing distribution story, and paid it in bash. Their ref file is a manifest; their checkout cache is a package manager; their --check targets are verify; their hand-maintained lists are a file-class model; their PR loop is the contribution process. TRex should absorb each one.

3 · Requirements

Each requirement is specific and carries an acceptance test. "Child" means any downstream consumer; "reference child" is hypershell.

IDRequirementAcceptance test
R1 Single-version dependency. A child shall depend on exactly one TRex module path, and one version of it, for all framework packages and generators it consumes. go list -m all in a fresh child shows exactly one rh-trex-ai entry. Reference child's three pins (two go.mod pseudo-versions + ref file) collapse to one.
R2 Resolvable releases. Every published TRex release shall be fetchable by tag from a clean environment with no sibling checkout. CI job: in a scratch module, go get github.com/openshift-online/rh-trex-ai@<tag> then build; fails today for v0.0.32–v0.0.35.
R3 Checkout-free tooling. All repo-coupled generation (scaffold, entity, add-field, remove, upgrade, verify) shall run in a child without cloning TRex. Container with only Go + git: go install …/cmd/trex-gen@vX, then scaffold and generate a kind that compiles. No ~/.cache/…/rh-trex-ai, no ref file.
R4 Template atomicity. A generator version shall imply exactly one template set; no template files shall be required on disk to generate. Templates are go:embeded; installing the tool leaves no template files; two runs at one version render byte-identical output.
R5 Correct scaffold. trex-gen init shall produce a project that builds and passes its own tests after only documented placeholder replacement. CI runs init in a scratch dir and make binary && make test succeeds. (Today's scaffold cannot resolve its imports at all.)
R6 Non-destructive upgrade. trex-gen upgrade shall never silently modify a child-owned file; it shall regenerate mechanical files, and shall report — not overwrite — owned files and overrides whose upstream template changed. Dry-run shall be the default. Golden-child fixture in CI: run upgrade across a minor version bump; assert owned files byte-identical, mechanical files updated, report lists every drift; no file changes under dry-run.
R7 Provenance and drift detection. Every generated file shall carry machine-readable generator identity and class; a manifest shall record kinds, options, and per-file render hashes; trex-gen verify --check shall exit non-zero on drift. CI gate replaces hypershell's hand-rolled --check targets: edit a mechanical file, verify --check fails; regenerate, it passes.
R8 Customization without forking. Child customization shall be expressible only through (a) owned files at documented seams, or (b) per-file template overrides recorded in the manifest. Upgrade shall surface upstream changes to overridden templates. Fixture child overrides one template and edits one owned seam file; upgrade reports the upstream template diff and leaves both intact.
R9 Reusable codegen library. TRex shall export its codegen primitives — naming/pluralization, field model and type maps, template function library, output planning, OpenAPI wiring — as a public, tested package. A fixture child-specific generator built purely on the public API renders a working kind; the reference child's vendored generator forks become deletable.
R10 Versioned skill distribution. TRex skills shall be installable into a child at a pinned version and upgradable without clobbering child-added skills, through a mechanism that does not require the child to duplicate the tree. Fresh child gains the TRex skill set; a skills sync updates TRex-owned files only; child-local categories (e.g. hypershell's security/, web-console/) are untouched and never conflict.
R11 Grow-then-promote flow. A child improvement shall land locally via a seam or recorded override, then move upstream as one PR with fixture tests, then reach all children via a version bump — with each step documented. The reference child's documented PR loop (RECONCILE.md: PRs #64/#65) is reproduced using only seams/overrides and trex-gen, with no manual re-pinning choreography.
R12 Scope boundary. TRex specs and skills shall contain no child-specific names or logic. CI lint greps the TRex tree for reference-child kind names (gateways, managedClusters, …) and fails on any hit outside fixtures.

4 · Preferred solution

4.1 · S1 — Restore one versioned root module

Return the repository to a single root Go module — module github.com/openshift-online/rh-trex-ai — containing the framework packages (pkg/…, plugins/…), the service entry points (cmd/…), and every generator (the entity generator, plus cli-, sdk-, console-plugin-, tui-generator, and openapi-ir as importable packages with thin main wrappers). Cut v0.1.0 on that shape. The nested components/control-plane service may remain a nested module — it is a consumer of the framework, not part of its API.

Why this is the keystone: a single module gives every artifact a child touches — framework packages, entity templates, spec-consumer generators — one version, one tag, one go get. It directly collapses hypershell's three-pin skew (R1) and makes every release resolvable (R2). It also ends the vendored-fork failure mode: go run github.com/openshift-online/rh-trex-ai/scripts/tui-generator@v0.1.0 works from any machine, no checkout, no cache, no ref file (R3).

Cost, paid once: hypershell re-paths its imports from …/components/api-server/pkg/… to …/pkg/… — a mechanical rewrite across one repo — and deletes its vendored generator forks and checkout cache. The retired consumer is unaffected (frozen at v0.0.31 on the old root path, which this change incidentally makes resolvable again, though nothing depends on that).

The root module is a new lineage, not a continuation of v0.0.31: semver obligations restart at v0.1.0 and the release notes must say so plainly. Tags v0.0.32–v0.0.35 should be documented as unresolvable-by-design artifacts of the transition.

4.2 · S2 — trex-gen: one checkout-free generator CLI

Move the entity generator out of components/api-server/scripts/generator.go into cmd/trex-gen as a proper CLI with subcommands mirroring the existing skill surface:

trex-gen init      [--repo] [--project] [dir]     # scaffold a new child (replaces templates/new-project + new-project skill copying)
trex-gen entity    --kind K [--fields …] [--plural P]
trex-gen add-field --kind K --field name:type[:required]
trex-gen remove    --kind K
trex-gen upgrade   [--dry-run] [--take-upstream F] [--keep F]
trex-gen verify    [--check]
trex-gen skills    sync | status

Design constraints: the tool stays dependency-light (stdlib + pflag) so installation is fast and its module graph stays inside TRex's dependency-age policy; entity templates are embedded with go:embed (R4); all flags the current script accepts (--library, --repo, --project, --proto-package) are preserved so generation semantics do not change — only acquisition does. The spec-consumer generators keep their existing entry points and remain directly runnable via module-aware go run <pkg>@<tag>; trex-gen does not wrap them, avoiding a second API for the same thing.

4.3 · S3 — Two-class generated code, a manifest, and a real upgrade

Formalize the split hypershell already maintains by hand. Every file the entity generator writes is classed:

ClassFilesUpgrade behavior
Mechanical
regenerable, DO NOT EDIT		 model.go, dao.go, mock_dao.go, presenter.go, handler.go, grpc_handler.go, grpc_presenter.go, migration.go, factory_test.go, testmain_test.go, openapi.{kinds}.yaml, {kinds}.proto Deleted and re-rendered on upgrade if and only if the on-disk file still hashes to the manifest's recorded render hash. If the child edited it, the file is a conflict: reported, never silently overwritten, resolved per-file with --take-upstream/--keep.
Scaffold-once
child-owned		 service.go, plugin.go, integration_test.go, grpc_integration_test.go Created only when absent (the pattern TRex's own CLI generator already specifies for main.go in CG-002). When the upstream template changes after creation, upgrade prints the old→new template diff so the child can port deliberately.

Headers make class and provenance machine-readable:

// Code generated by trex-gen v0.1.0 kind=Gateways class=mechanical hash=sha256:9f2c…  DO NOT EDIT.
// Code generated by trex-gen v0.1.0 kind=Gateways class=scaffold  EDITABLE: created once; `trex-gen upgrade` reports template drift.

A .trex.yaml manifest at the child's api-server root replaces rh-trex-ai.ref, the hand-maintained file lists, and the drift targets. It records the trex-gen version, every kind with its fields and options, template overrides, and per-file render hashes:

version: v0.1.0
kinds:
  - kind: Gateways
    fields: "name:string:required,endpoint:string"
    files:
      dao.go:      {class: mechanical, hash: sha256:…}
      service.go:  {class: scaffold,   created: v0.1.0}
overrides:
  - template: generate-handler.txt

trex-gen upgrade therefore does, in one supported command, what hypershell's trex-checkout.sh + generate-*.sh --check + rh-trex-ai.ref + manual pseudo-version bumps do today — and does it without a checkout and without trusting a cached tree ("refuses a checkout whose files were modified" becomes moot when there is no checkout).

4.4 · S4 — Customization seams and template overrides

Seams are where child code is allowed to live. The model is already proven in the field — hypershell's components/api-server/plugins/otel and components/api-server/plugins/rbac are cross-cutting plugins that register middleware and interceptors through the framework's init() registry without touching generated files. TRex should document and commit to the seam set:

CustomizationSeamEvidence it works
Business logic, event reactions, field validationservice.go (scaffold-once): OnUpsert/OnDelete, a Validate() hookExisting service event handlers; hypershell kinds carry custom logic here
Cross-cutting middleware, interceptors, telemetryOwn plugin package registering via init()hypershell components/api-server/plugins/otel, components/api-server/plugins/rbac
Routes and alternate prefixesFramework registration APIRegisterPrefixedRoutes (restored by PR #65, driven by hypershell's need)
Generated-code shapePer-file template override (below)Replaces generator.go forks

One deliberate seam change rides along: handler validation moves into the service. Today TRex's own add-field skill instructs children to edit the (mechanical) handler.go to add PATCH validation — which would make every validated kind a permanent upgrade conflict. Handlers must stay purely mechanical; validation belongs in the owned service layer. This is a template fix in TRex, not a child obligation.

Template overrides replace forking: trex-gen entity --templates-dir my-templates/ shadows the embedded set per file — override generate-handler.txt only, inherit the rest. Overrides are recorded in the manifest, and on upgrade TRex reports the upstream diff of every overridden template (the same conffile courtesy Debian extends to administrators). Growing a local override and promoting it upstream (R11) is then a single move: delete the override, PR the template change with a fixture, release.

4.5 · S5 — Export the codegen primitives (pkg/codegen)

Promote the generator's reusable internals to a public, tested package: pluralization and naming transforms, the field model and type maps (Go/DB/OpenAPI/proto), the template function library, output path planning, and OpenAPI auto-wiring. Children with their own entity flavors — the retired consumer forked the entire generator for this reason — compose pkg/codegen instead of copying generator.go. The entity templates themselves remain the one canonical set TRex ships; pkg/codegen is the escape hatch for shapes TRex deliberately does not own.

4.6 · S6 — Versioned skill distribution

Skills are markdown directories, so distribution is a file-ownership problem, not a code problem. The mechanism mirrors the two-class model:

  • TRex-owned skill files carry a version marker (front-matter trex: v0.1.0). trex-gen skills sync refreshes exactly those files, verifiable with trex-gen skills status. Harness-agnostic: works for Claude Code, and for any agent that reads a skills/ or AGENTS.md tree — which matters, because hypershell runs multiple agent harnesses.
  • Child-owned skills — hypershell's security/, web-console/ — are never touched by sync. Conflicts (child edited a TRex-owned file) are reported, not overwritten.
  • For Claude Code specifically, the same tree additionally ships as a versioned plugin, so a child can consume skills without any local copy at all. The plugin is packaging of the same files, not a second source of truth.
  • Contributing back is a PR against TRex's skills/, after which every child gets it on the next sync — deleting today's fork-and-drift pattern.

4.7 · S7 — Governance, CI, and release discipline

  • Release checklist: tag on the root module; release notes must carry a generated-code changelog — which templates changed, which classes affected — because that is what trex-gen upgrade reports against. Move to v1.0.0 quickly: v0.x semver promises nothing, and children pinning a framework need the promise.
  • CI gates implementing the requirements: R2 (scratch-module resolution), R5 (scaffold builds), R6 (golden-child upgrade fixture), R7 (drift check), R9 (public-API child generator fixture), R12 (scope lint). The golden-child fixture should be generated by trex-gen init itself, not hand-maintained.
  • Spec alignment: CG-001 gains the file classes, headers, and manifest; the CG-002 "create only when absent" requirement is generalized into CG-001 for entity files; components/api-server/scripts/generator.md's stale output table is corrected or deleted (it still documents the pre-plugin layout).
  • Dependency-age and supply chain: trex-gen's module graph is inside the root module, so the existing dependency-age policy governs it — and hypershell can drop the --external-go-mod/--external-repo machinery aimed into a cached checkout.

4.8 · S8 — Immediate repairs (regardless of everything else)

  1. Restore the root module and cut a resolvable tag (S1) — nothing else is consumable until this lands.
  2. Fix or regenerate templates/new-project/: correct module paths, honest README, generator delivered via trex-gen init rather than a claimed-but-absent scripts/ directory.
  3. Update the root CLAUDE.md cleanup instructions and generator.md output tables to the plugins-based layout.
  4. Document the fate of tags v0.0.32–v0.0.35 so nobody "upgrades" into them.

5 · Alternatives considered

IDAlternativeAssessment
A1 Pure runtime framework — no codegen. Everything via registry, interfaces, generics; kinds declared in data, not generated. Rejected as the primary model. Proto/gRPC stubs, OpenAPI documents, and SQL migrations are inherently declarative-to-code artifacts; TRex's own specs (CG-001…006) and both consumers' plugin trees are built around generated kinds. However, the principle is sound where it applies — the TUI runtime (CG-006) is already descriptor-driven generic code, and cross-cutting concerns already live in runtime plugins. The proposal keeps runtime the default and codegen the exception, shrinking the generated surface over time.
A2 Template-sync tooling (git subtree, copier, yeoman): apply and re-apply a template repo over the child. Rejected as the primary model: it has no library axis at all — the framework and its version would be indistinguishable from the scaffold — and re-application is merge-heuristic territory. Borrowed its one good idea: an answers/state file (copier's .copier-answers.yml) becomes the .trex.yaml manifest.
A3 Status quo multi-module + pseudo-versions. Keep components/api-server as the module; children pin pseudo-versions; generators run from checkouts. Rejected on evidence: this is precisely today's state, and its observed output is a frozen retired consumer, a live consumer maintaining three pins with drift, four unresolvable tags, vendored generator forks, and a cached-clone bash layer. Nothing here needs hypothesizing.
A4 Keep the nested path, add nested tags. Zero import churn for hypershell; tag every release components/api-server/vX.Y.Z. The strongest counter-proposal, and the honest runner-up. It fixes resolvability (R2) without touching the live child. It loses on the longer horizon: the …/components/api-server/… prefix becomes the framework's permanent public identity — long imports, a "component of TRex" framing that contradicts "TRex is the parent product," a per-release nested-tag tax with the v0.0.32–35 failure mode one distraction away from repeating, and no natural home for the generators (nested tags × five generator modules). The one-time mechanical re-path of a single live consumer is cheaper than a forever tax. See the defense matrix.
A5 Protected-region markers inside single files (// trex:begin:custom … // trex:end). Rejected in favor of the file-split: markers merge badly, are invisible to tooling that greps files, and invite drift when children edit around them. TRex already rejected this shape once — CG-002 specifies create-if-absent plus a regenerated registration file instead — and the file-split is the same decision applied to entities.
A6 Generate at build time, never check in generated code. Rejected for developer experience: generated files must be readable, greppable, reviewable, and IDE-indexed; both consumers check in their plugin trees. Determinism plus a CI drift gate (trex-gen verify --check) delivers the same integrity without hiding the code.

8 · Review 1 — Senior Distinguished Architect

Persona: a strict, seasoned reviewer — twenty-five years of platform libraries, generator frameworks, and the scars of three corporate scaffolding initiatives that died in production. Thorough but fair. Critical lens: ease-of-use and usability for the consuming engineer.

Overall assessment — CONDITIONAL APPROVAL. The diagnosis is exemplary and the direction is correct: the document does what too few architecture proposals do — it derives requirements from observed consumer behavior rather than imagination, and its central move (productize the child's hand-built workarounds) is exactly right. I endorse S1, S2, and the hash-gated upgrade model. However, I raise two blockers, three majors, and four minors. The blockers are not objections to the architecture; they are places where the proposal understates difficulty it has already discovered evidence for. Fix them before implementation begins.

Findings

F1 Blocker — The class boundary is aspirational precisely where the proposal needs it to be load-bearing

The two-class model (§4.3) is presented as settled, and the document itself supplies the refutation: TRex's own add-field skill instructs children to edit handler.go — a mechanical file — to add PATCH validation. The proposal notices this and prescribes moving validation into the service seam (§4.4). Good. But it treats that as a template tweak. It is a migration problem: every kind the live child has already generated may carry child edits inside files the new model declares mechanical, and the hash-gating that would detect this starts recording only at first trex-gen adoption. The proposal must specify the adoption baseline honestly: on first run against an existing child, the manifest records current files as-rendered at adoption time, meaning pre-existing child edits inside mechanical files are invisible until the next template change collides with them. State this, and provide trex-gen verify --diff-against-template so a child can audit its mechanical files for local edits before opting into hash gating. Usability means the tool tells me what I do not know about my own codebase.

F2 Blocker — The version-skew evidence indicts more than the module layout

Hypershell's three pins at two versions (§2.2) is cited as justification for the single root module. Correct — but note the skew persisted even though one team owns both repos. That tells you the cost of manual pin reconciliation is high enough to defer even when the deferrer is the author. The single module fixes the structure, but the proposal should verify the failure cannot re-emerge through its own back door: the spec-consumer generators remain separately runnable via go run <pkg>@<tag> (§4.2), which reintroduces per-invocation version choice. Require that the child's manifest be the single source for those invocations too — a trex-gen run <generator> shim or a documented Makefile pattern that reads the manifest — or in eighteen months there will be five pins again, three of them accidental.

F3 Major — Scaffold-once test files will rot, and the proposal under-answers

Classifying integration_test.go as child-owned (§4.3) is right for ownership and wrong for freshness: when the mechanical handler surface changes (new field, new error contract), the child's owned tests silently decay from "tests" into "historical documents." The template-changelog release requirement (§4.7) helps upstream, but the child engineer's question at upgrade time is "which of my files are affected?" Upgrade must map template changes onto the child's manifest: "you own integration_test.go created at v0.1.0; templates for it changed in v0.2.0; here is the diff and the kinds affected." Without that mapping, the changelog is a document nobody reads. Additionally, testmain_test.go and factory_test.go being mechanical while their sibling integration tests are owned will split test infrastructure across classes — justify that split explicitly or unify the test file treatment.

F4 Major — Skills distribution is underspecified where it is hardest

§4.6 is the weakest section relative to its difficulty. Three specifics. First, "version marker in front-matter" — define conflict semantics precisely: a TRex-owned file the child edited is a conflict like any other; sync must never overwrite it, and status must list it. Second, the plugin is described as "packaging of the same files, not a second source of truth," but nothing enforces that; require CI to generate the plugin from the tree so drift is impossible rather than discouraged. Third, skills ride the module version — but skill fixes (a wrong command in a procedure) will then be gated on the release train. Specify whether skills may ship in patch releases independently, or accept that a typo in a procedure waits for a tag. Choose deliberately; do not discover the answer in an incident.

F5 Major — Missing non-functional requirements

The requirements table (§3) is functional. Absent: supply chain — go install at a version implies trust in the module proxy and the tag; the dependency-age policy already governs the module graph, but state that trex-gen inherits it and that tags are ideally signed or at least immutably documented; offline/air-gapped builds — hypershell-style platform teams build in restricted networks; go:embed plus a single module is actually excellent for this, but say so as a requirement, and verify go run <pkg>@tag has a vendorable equivalent; determinism across platforms — the current generator shells out to make proto and gofmt; specify toolchain expectations (buf, protoc) as part of R3's acceptance test rather than leaving the child to discover them at runtime. And note that determinism requirements already exist in CG-005/CG-006 — reference, don't restate (DRY applies to specs too).

F6 Minor — The v0.1.0 → v1.0.0 recommendation is right but the scoping hint is buried

§4.7 says move to v1.0.0 quickly and, in the defense matrix, scopes the v1 contract to the twelve packages hypershell consumes. Promote that scoping into the release plan proper: publish the v1 package list in the release notes of v0.1.0 so consumers can see the shape of the promise from day one.

F7 Minor — Concept budget

The proposal introduces, in order: root module, trex-gen, two file classes, manifest, render hashes, seams, template overrides, skills sync, plugin packaging. Five of those are load-bearing for the happy path. The quickstart implied by §4.2 must be an explicit, documented, four-command happy path — init, entity, db, run — with every other concept introduced only at the moment it is needed (upgrade when first upgrading, overrides when first overriding). The measure of this architecture is not the reviewer's comprehension; it is the child engineer who never reads this document and still never forks a template.

F8 Minor — Golden-fixture maintenance

R6's acceptance rests on a golden child in CI. Specify its lifecycle: it should be regenerated by trex-gen init at each release and versioned alongside, so template changes update it mechanically rather than by hand-tending. Otherwise the fixture becomes the first thing skipped in a rush and the upgrade guarantee silently expires.

F9 Minor — Control-plane placement needs one paragraph of justification

§4.1 waves control-plane into a nested module in a clause. It is the right call (it is a service, not API), but state the rule — "framework API lives at the root; deployable services built on the framework are nested modules" — so the next component added lands in the right place by rule rather than by memory.

F10 Endorse — The evidence method is the document's greatest strength; make it permanent

Deriving requirements from the reference child's actual workarounds (§2) is what gives this proposal its authority. Make that a standing gate, not a one-time method: hypershell (or its successor) should appear in TRex CI as the conformance child — the golden fixture of P2 should, at minimum, be generated by the same trex-gen that the live child runs, in the same release. Dogfooding is the only durable defense against the scaffold-rot this repository has already demonstrated.

Disposition. Resolve F1 and F2 (both are specification gaps, not design changes), tighten F3–F5 in the spec phase (P0), and proceed. The architecture itself — one module, one tool, hash-gated ownership, documented seams — I would defend in any forum. The job now is to make the specification as honest as the evidence behind it.

9 · Review 2 — The Pragmatic Programmer (fresh eyes)

Seeded persona: a reviewer from the School of the Pragmatic Programmer — DRY, orthogonality, tracer bullets, broken windows, "don't live with software you wouldn't be proud of," a deep suspicion of wizard code nobody understands, and a strong preference for reversible decisions. This reviewer received the document cold, with no authoring context, and was asked to review the solution and to validate or reject each finding of Review 1.

Overall assessment — APPROVED, NARROWER THAN WRITTEN. I came in cold and fact-checked Section 2 against both working trees before reading the solution: the ref file (ff48c56…, as claimed), the HAND_MAINTAINED skip list and --check mode in scripts/generate-cli.sh, two pseudo-version pins at two commits, the vendored generator forks, the #64/#65 loop in hypershell's skills/RECONCILE.md, four tags with no root go.mod, a scaffold importing rh-trex-ai/pkg/cmd from a module that does not exist, and generator.md documenting the pre-plugin layout while generator.go writes plugins/{kinds}/. All real. A requirements list that is a live customer's workaround inventory is not guessing — it is productizing, and that earns the direction. But the proposal spends that credibility twice: a third of the machine (template overrides, the codegen library, the skills sync) serves elegance or a retired consumer, not the live one. Ship the keystone, cut the wings, widen on evidence.

Findings on the proposal

PP1 Endorse — The evidence method is the spine, and it survives adversarial checking

Every row of §2.1 I tested resolved to a real artifact. Hypershell really maintains three pins at two versions; its reconcile notes really record "its generators are byte-identical in the new commit" as the reason the ref file stayed behind; sixteen plugins really sit under components/api-server/plugins/, including the otel and rbac cross-cutters cited as seam evidence. Requirements derived from what a customer actually built is the difference between architecture and art criticism, and it is why this document deserves a serious review rather than a polite one.

PP2 Endorse — S1 is right, and it is a reversibility argument, not an aesthetic one

Import paths are the one decision here that is genuinely expensive to reverse; everything else — CLI shape, manifest format, class names — is cheap to change later. Pay now on the irreversible thing; stay minimal everywhere else. A4 (nested tags) is the cheap-now option that taxes forever: …/components/api-server/… as permanent public identity, nested-tag discipline with the v0.0.32–35 failure mode one distraction from repeating, and no natural home for five generator modules. I verified the rot S1 fixes: v0.0.31 carries a root go.mod; v0.0.32–v0.0.35 carry none; no nested tags exist.

PP3 Major — Template overrides have no demonstrated consumer; defer them and R8

Neither consumer ever overrode a single template. The retired consumer forked the whole generator; the live one extended a vendored fork — both are acquisition failures that importable packages (S1) fix directly, and behavior changes already travel upstream well: #64 went from noticed to merged and tagged in days. The override machinery — shadow directories, manifest recording, upgrade-time diffs, a promotion protocol — is a fork with better manners, and the proposal names its own disease: "override sprawl hides upstream improvements." Defer §4.4's override half and R8; build the mechanism when a real override exists to migrate.

PP4 Major — Skills: two distribution mechanisms proposed; ship one

S6 ships a version-marked file-sync (skills sync/status, conflict semantics, release-train questions) and a versioned plugin, described as "packaging of the same files." Two mechanisms for distributing markdown is one too many. The plugin alone covers the named harness; sync exists for "multiple agent harnesses," a future need. Cut the sync, keep the plugin generated from the tree in CI, and R10 halves. If a harness without plugin support appears, sync is a weekend build against the same source of truth.

PP5 Major — pkg/codegen is designed for a retired customer; demote R9

R9's justification is "the retired consumer forked the entire generator for this reason." Building a public, tested primitives API — naming, field model, type maps, template functions, output planning — for a dead consumer is spec-driven speculation. The live child's vendored forks exist because the modules were not importable; S1 deletes them without pkg/codegen. Keep the generator packages importable in the root module; promote specific primitives when a child composes them in anger. The escape hatch is the import, not a framework.

PP6 Major — The Validate-seam move is a child port mislabeled "not a child obligation"

§4.4 is right that handlers must stay mechanical — I verified the rot it fixes: skills/build/add-field/SKILL.md, step 5, instructs children to edit plugins/{kindLowerPlural}/handler.go and "add validation if the field is required." But the fix becomes a child obligation the moment the child upgrades: every kind whose handler carries validation edits becomes an upgrade conflict at once — and per F1, pre-adoption edits may not even be flagged. Sequence it: adoption first, with F1's audit; the Validate change in a later minor; upgrade printing the template diff beside the file's local diff so the port is mechanical.

PP7 Minor — Don't gate the keystone on documentation work

S8 declares the repairs immediate "regardless of everything else," yet the phase table puts spec-and-doc reconciliation (P0) ahead of the module restore (P1). The restore is days of mechanical work and unblocks everything; the doc repairs can ride the same PR train. Tracer-bullet ordering: cut the resolvable tag first, prove it from a scratch module in CI, reconcile the paper while it runs. A phase zero made of prose is where urgency goes to die.

PP8 Minor — R11 is process wearing a requirement's badge

The grow-then-promote loop already works end to end — hypershell proved it: missing 422 → PR #64 → tagged; dropped route → PR #65 → tagged; re-pin; ref file deliberately left behind after verifying byte-identical generators. What made it costly was the unresolvable tag, which S1 fixes. After S1, R11 is satisfied for free; keep it as documentation of the loop, not as a fixture-tested requirement that generates ceremony for every two-line template fix.

PP9 Minor — v1.0.0 "quickly" promises stability during the storm, and the scoping number is wrong

v0.x is the cheap state — you are allowed to break things. The proposal schedules its largest churn (re-templating, the Validate port) inside v0.x and then wants the compatibility promise early. Also: the defense matrix scopes the v1 contract to "the twelve hypershell consumes" — hypershell actually imports about twenty-one distinct framework packages, a surface two-thirds larger than the doc believes. Publish the candidate list at v0.1.0 (accurately counted), run one real minor-to-minor upgrade of the live child, and cut v1.0.0 on that evidence.

PP10 Endorse — The manifest and hash-gated upgrade is the DRIEST thing here, and it serves the resident engineer

Today "what the generator did" lives in four places — ref file, two pseudo-version pins, the HAND_MAINTAINED list, the --check targets. The manifest plus go.mod collapses that to two, split along the one axis that is genuinely orthogonal: library version is Go's business, generation state is the tool's. The two-class model is kind to the engineer who lives inside it: class and provenance travel in a grep-able header (the DO NOT EDIT convention every Go hand knows from protobuf), conflicts resolve per-file with explicit flags instead of merge heuristics, and scaffold-once files are honestly labeled.

Verdict on Review 1

F1 Validated

That the unspecified adoption baseline lets pre-existing child edits inside mechanical files be absorbed, then clobbered.

The blocker stands. The document never says what first-run adoption records, and R6's acceptance test — a golden child upgraded across a minor — never exercises adoption-of-an-existing-child, the only live customer's actual first experience. Record-on-disk-as-baseline means the first post-adoption template change silently overwrites pre-adoption edits, violating "never silently modify a child-owned file" in every sense that matters. The prescribed verify --diff-against-template audit is cheap and right: make adoption the audit. That is the difference between R6 being a guarantee and being marketing.

F2 Validated w/ revision

That separately runnable go run <pkg>@<tag> generators reintroduce per-invocation version choice.

The back door is real: a tag typed into a Makefile is a pin outside the manifest, and this team's demonstrated behavior is letting pins drift even while owning both repos. But this is a convention plus a gate, not an architecture change — downgrade to major. Take F2's weaker prescription, the documented Makefile pattern reading the manifest, and make verify --check fail on tool-versus-manifest version mismatch. I reject the trex-gen run shim: §4.2 was right to refuse a second API for the same thing, and the shim recreates it.

F3 Validated

That owned test files rot into historical documents, and the test-class split needs justification.

Right on both halves. The release-notes changelog is upstream-centric; the child's question is "which of my files," and the manifest already records kinds and creation versions, so mapping template changes onto affected kinds is nearly free — do it. On the split: factory_test.go mechanical and integration_test.go owned is defensible (boilerplate versus the child's assertions), but an engineer seeing two sibling test files treated differently will invent a wrong reason unless CG-001 states the real one.

F4 Validated w/ revision

That skills distribution is underspecified on conflicts, plugin drift, and release gating.

The gaps are real where the mechanism exists — but my revision is bigger than the finding: cut the sync mechanism (PP4) and keep the plugin. Conflict semantics then vanish, release-train gating becomes a plugin-release question answered once, and the one requirement that fully survives is the best one: generate the plugin from the tree in CI so drift is impossible rather than discouraged. F4's lasting point: never leave a "same source of truth" claim to discipline when a make target can enforce it.

F5 Validated w/ revision

That supply-chain, air-gapped, and toolchain-determinism requirements are missing.

The toolchain clause is load-bearing and I would raise it: R3's acceptance test says "container with only Go + git… generate a kind that compiles," but the repo's own instructions require make proto (protoc and plugins) before anything compiles. As written, R3's test cannot pass. Name the tools in the acceptance test. The DRY point — reference CG-005/CG-006, don't restate — is sound. Air-gapped deserves one sentence in R3 (GOFLAGS=-mod=vendor). I reject the signed-tags clause: no demonstrated verifier exists; that is ceremony, not supply chain.

F6 Validated w/ revision

That the v1 scoping hint should be promoted into the release plan.

Publishing the v1 package list at v0.1.0: yes, cheap, do it — but count it first (PP9: ~21 packages, not twelve). Where I part ways is F6's premise that moving to v1.0.0 quickly is "right": a compatibility promise made before the first real upgrade cycle is a guess. Publish the candidate contract at v0.1.0; cut v1.0.0 after the reference child completes one live minor-to-minor upgrade. One clean upgrade is worth more than any scoping document.

F7 Validated w/ revision

That the concept budget is high and the happy path must be explicit.

The concern is my school's own rule, so yes. But the prescription — document a four-command happy path, introduce concepts just-in-time — treats the symptom. The right fix is fewer concepts: cut overrides (PP3) and skills sync (PP4) and the count drops from nine to six, four of which carry the happy path. Documentation cannot save a design that fronts its rarely-used machinery; the child engineer who never reads this document is the only acceptance test that matters.

F8 Validated

That the golden fixture needs a lifecycle: regenerated at each release, versioned alongside.

Valid, with a caveat about novelty: §4.7 already says the fixture is generated by trex-gen init, not hand-maintained — F8's real increment is the timing and versioning. That increment is load-bearing, because R6's acceptance test ("upgrade across a minor version bump") requires two versions of the fixture to exist. Without the lifecycle, the guarantee's proof expires with the first rushed release.

F9 Validated

That control-plane's placement deserves a stated rule, not a clause.

Cheapest finding in the set, and correct. The rule — framework API at the root, deployable services as nested modules — matches how the repo already works (components/control-plane is a nested module today, correctly, because it is a consumer). Rules beat memory for the next component someone adds at 5pm on a Friday. One paragraph; write it.

F10 Validated w/ revision

That the reference child should be a standing conformance gate in TRex CI.

The dogfooding principle is right — this repository already demonstrated the alternative: a scaffold whose README claims a generator it does not ship (verified in templates/new-project/). But hard-wiring a live product repo into TRex's blocking CI couples two release trains; the child's churn would block the parent. Take the scheduled version: conformance runs against live hypershell at each release, blocking gate on the generated golden child, produced by the same trex-gen the live child runs. Endorse the principle, revise the mechanism.

Disposition — BUILD THE KEYSTONE, CUT THE WINGS. Before implementation: specify the adoption baseline and its audit (F1 — the difference between R6 being a guarantee and a hope); define the manifest-driven invocation pattern for spec-consumer generators and fail verify --check on version mismatch (F2, as convention, not a shim); put toolchain expectations into R3's acceptance test (F5); sequence the Validate-seam port after adoption with a per-kind impact map (PP6, F3); state the module-placement rule (F9). Cut outright: template overrides and R8, the skills sync mechanism (keep the CI-generated plugin), and pkg/codegen as a designed public API — restore any of them the day a real consumer asks. Keep: S1, S2, S3's manifest and hash gating, S4's seams and the Validate fix itself, S8's repairs, the A4 defense, the evidence method. Net on Review 1: strong work — 4 of 10 findings stand as filed (F1, F3, F8, F9), 6 stand with revised prescriptions or downgraded severities (F2, F4, F5, F6, F7, F10), none rejected outright, though I reject two clauses inside them (the trex-gen run shim in F2, signed tags in F5) and cut one blocker to major. Review 1 diagnoses the document's honesty gaps better than it prescribes fixes, which lean toward process. The proposal's center of gravity — one module, one tool, hash-gated ownership, real seams — I would ship tomorrow. The ornamentation I would not ship at all.
