# Console UI Specification

**Date:** 2026-07-07
**Status:** Draft
**ID:** APP-002
**Related:** [Managed API Platform](managed-api-platform.spec.md), [Console Plugin Generator](../codegen/console-plugin-generator.spec.md), [REST Conventions](../api/rest-conventions.spec.md)
**Implements:** Generated output from CG-004 (`scripts/console-plugin-generator/`), customized for the Managed API Platform entities

---

## Overview

The Console UI is a React/TypeScript web application that provides a visual interface for the Managed API Platform (APP-001). It is generated by the Console Plugin Generator (CG-004) from the project's OpenAPI specification, then customized with platform-specific workflows that go beyond generic CRUD.

The UI serves two deployment targets:

- **OpenShift Console Plugin** — Integrates as a dynamic plugin in OpenShift Console via the ConsolePlugin CRD. Uses `consoleFetch` for proxied API access through the console backend.
- **Standalone SPA** — Runs independently as a single-page application served by nginx or any static file server. Uses direct `fetch` against the TRex API server. Useful for local development, demos, and non-OpenShift deployments.

Both targets share the same React component tree. The only difference is the API client layer: `consoleFetch` (OpenShift) vs `window.fetch` (standalone).

## Generation

The base UI scaffold is produced by CG-004:

```bash
cd scripts/console-plugin-generator
go run . --spec ../../openapi/openapi.yaml --out /tmp/trex-console --name trex-console
```

This generates list pages, detail pages, and create forms for all 5 APP-001 entities (Projects, EntityDefinitions, FieldDefinitions, Relationships, Builds) plus Dinosaurs (the example entity).

### Post-Generation Customization

The generated scaffold provides generic CRUD. The following customizations transform it into a purpose-built API platform console:

| Customization | Description | Generated Baseline |
|---------------|-------------|--------------------|
| Project dashboard | Landing page showing project status, entity count, latest build status | Generic list page |
| ERD visual editor | Interactive entity-relationship diagram rendered from EntityDefinitions + Relationships | No equivalent |
| Build trigger + log viewer | One-click build trigger with live status polling and scrollable build log display | Generic create form |
| Parent-scoped navigation | Selecting a project filters EntityDefinitions, Relationships, and Builds automatically | No cross-entity filtering |
| Status badges | Color-coded status chips for Project status and Build status | Plain text display |
| Field type selector | Dropdown constrained to valid field types (`string`, `int`, `int64`, `bool`, `float`, `time`) | Free-text input |
| Relationship type selector | Dropdown constrained to valid relationship types with source/target entity pickers | Free-text input |

## Requirements

### Requirement: Generated CRUD for All Entities

The console UI SHALL provide list, detail, and create views for all APP-001 entities: Projects, EntityDefinitions, FieldDefinitions, Relationships, and Builds.

#### Scenario: Entity list with pagination and search
- GIVEN the console UI is loaded
- WHEN a user navigates to any entity list page (e.g. Projects, Entity Definitions)
- THEN the page SHALL display a paginated table with search
- AND each row SHALL link to the entity's detail page
- AND a "Create" button SHALL navigate to the create form

#### Scenario: Entity detail view
- GIVEN a user clicks an entity ID in the list page
- WHEN the detail page loads
- THEN all entity fields SHALL be displayed in a description list
- AND a "Delete" button SHALL be available for soft-deletable entities

#### Scenario: Entity create form
- GIVEN a user clicks "Create" on a list page
- WHEN the create form is displayed
- THEN all writable fields SHALL have form inputs matching their types
- AND required fields SHALL be marked with a required indicator
- AND submitting the form SHALL POST to the API and redirect to the detail page

### Requirement: Project-Scoped Navigation

The console UI SHALL support project-scoped browsing where selecting a project filters all child entities.

#### Scenario: Project context propagation
- GIVEN a user is viewing a Project's detail page
- WHEN they navigate to "Entity Definitions" from that context
- THEN the entity definitions list SHALL be pre-filtered by `?project_id={selected_project_id}`
- AND the create form SHALL pre-populate the `project_id` field

#### Scenario: EntityDefinition context to FieldDefinitions
- GIVEN a user is viewing an EntityDefinition's detail page
- WHEN they navigate to "Field Definitions" from that context
- THEN the field definitions list SHALL be pre-filtered by `?entity_definition_id={selected_entity_definition_id}`

### Requirement: Build Workflow

The console UI SHALL provide a streamlined build trigger and monitoring experience.

#### Scenario: Trigger a build
- GIVEN a user is viewing an active Project
- WHEN they click "Trigger Build"
- THEN a Build SHALL be created via `POST /builds` with the current project ID
- AND the UI SHALL navigate to the build detail page

#### Scenario: Build status polling
- GIVEN a user is viewing a Build detail page
- AND the build status is `pending` or `building`
- WHEN the page is displayed
- THEN the UI SHALL poll `GET /builds/{id}` at a regular interval (e.g. every 3 seconds)
- AND update the status badge and build log display in real time
- AND stop polling when the build reaches a terminal state (`succeeded` or `failed`)

#### Scenario: Build log viewer
- GIVEN a user is viewing a Build detail page
- AND the build has a non-empty `build_log`
- WHEN the page is displayed
- THEN the build log SHALL be displayed in a scrollable, monospace-font container
- AND new log content SHALL auto-scroll to the bottom during polling

### Requirement: Status Visualization

The console UI SHALL display entity statuses with visual indicators.

#### Scenario: Project status badges
- GIVEN a Project with status `draft`, `active`, or `archived`
- WHEN displayed in a list or detail page
- THEN the status SHALL be rendered as a color-coded label:
  - `draft` — grey/blue
  - `active` — green
  - `archived` — orange

#### Scenario: Build status badges
- GIVEN a Build with status `pending`, `building`, `succeeded`, or `failed`
- WHEN displayed in a list or detail page
- THEN the status SHALL be rendered as a color-coded label:
  - `pending` — grey
  - `building` — blue with spinner
  - `succeeded` — green
  - `failed` — red

### Requirement: Constrained Input Controls

The console UI SHALL use appropriate input controls for enumerated fields.

#### Scenario: Field type selector
- GIVEN a user is creating or editing a FieldDefinition
- WHEN they set the `field_type`
- THEN a dropdown SHALL be presented with options: `string`, `int`, `int64`, `bool`, `float`, `time`
- AND free-text entry SHALL NOT be allowed

#### Scenario: Relationship type selector
- GIVEN a user is creating a Relationship
- WHEN they set the `relationship_type`
- THEN a dropdown SHALL be presented with options: `has_one`, `has_many`, `belongs_to`, `many_to_many`

#### Scenario: Entity pickers for relationships
- GIVEN a user is creating a Relationship
- WHEN they set `source_entity_id` or `target_entity_id`
- THEN a searchable dropdown SHALL be presented listing EntityDefinitions in the same project
- AND each option SHALL display `kind_name (ID)` for clarity

### Requirement: ERD Visualization (Phase 2)

The console UI SHOULD include a visual entity-relationship diagram for a Project.

#### Scenario: ERD viewer
- GIVEN a Project with EntityDefinitions and Relationships
- WHEN a user navigates to the project's ERD view
- THEN entities SHALL be rendered as boxes with their field names and types
- AND relationships SHALL be rendered as labeled edges between entity boxes
- AND the diagram SHALL update when entities or relationships are added/removed

### Requirement: Standalone Deployment

The console UI SHALL support standalone deployment outside of OpenShift Console.

#### Scenario: Standalone build
- GIVEN the generated console plugin project
- WHEN built in standalone mode (`npm run build:standalone`)
- THEN the output SHALL be a static SPA bundle servable by nginx or any HTTP server
- AND API calls SHALL use direct `fetch` against a configurable API base URL
- AND the base URL SHALL be configurable via environment variable (`REACT_APP_API_URL`) or runtime config

#### Scenario: Local development
- GIVEN a developer running the API server locally (`make run-no-auth`)
- WHEN they run the console UI in development mode (`npm run dev`)
- THEN the UI SHALL proxy API requests to `http://localhost:8000`
- AND hot module reloading SHALL be enabled

## User Workflows

### Workflow 1: Define and Build an API (Demo Flow)

This is the primary demo workflow for showing the Managed API Platform in action.

```
1. Open Console UI → Projects list page
2. Click "Create Project"
   → Enter name: "pet-store", description: "Pet Store API"
   → Submit → redirected to project detail page

3. Click "Activate" button (sets status = active)

4. Navigate to Entity Definitions (filtered to pet-store)
5. Click "Create Entity Definition"
   → kind_name: "Pet", description: "A pet in the store"
   → Submit

6. Navigate to Field Definitions (filtered to Pet entity)
7. Create fields:
   → name: "name", type: "string", required: true
   → name: "species", type: "string", required: true
   → name: "age", type: "int", required: false

8. Create another entity: "Owner"
   → Field: "email", type: "string", required: true
   → Field: "pet_id", type: "string", required: true

9. Navigate to Relationships (filtered to pet-store)
10. Create relationship:
    → source: Owner, target: Pet, type: belongs_to
    → Submit

11. Navigate to project dashboard or ERD view
    → See visual diagram of Pet ←→ Owner relationship

12. Click "Trigger Build"
    → Watch build status transition: pending → building → succeeded
    → View build log showing generator output per entity

13. Build complete — generated code is in the build workspace
```

### Workflow 2: Iterate on an Existing Project

```
1. Open Console UI → Projects → select existing project
2. Add a new EntityDefinition (e.g. "Appointment")
3. Add fields to the new entity
4. Add a relationship: Pet has_many Appointments
5. Trigger a new build
6. Compare build logs between builds
```

## Deployment

### OpenShift Console Plugin

```bash
# Generate
cd scripts/console-plugin-generator
go run . --spec ../../openapi/openapi.yaml --out /tmp/trex-console --name trex-console

# Build
cd /tmp/trex-console
npm install && npm run build

# Deploy to OpenShift
oc apply -f deploy/
```

The plugin registers via the `ConsolePlugin` CRD and appears in the OpenShift Console sidebar under the configured navigation section.

### Standalone SPA

```bash
# Generate
cd scripts/console-plugin-generator
go run . --spec ../../openapi/openapi.yaml --out /tmp/trex-console --name trex-console

# Build standalone
cd /tmp/trex-console
npm install
REACT_APP_API_URL=http://localhost:8000 npm run build

# Serve
npx serve dist/
```

### Local Development

```bash
# Terminal 1: API server
make db/setup && ./trex migrate && make run-no-auth

# Terminal 2: Console UI
cd /tmp/trex-console
npm install
npm run dev
# → Opens browser at http://localhost:9001 with HMR
```

## Design Decisions

| Decision | Rationale |
|----------|-----------|
| Generate base scaffold with CG-004, customize post-generation | Leverages existing generator infrastructure; avoids building a separate UI generator. Post-generation customization adds platform-specific workflows (build trigger, ERD viewer) that are too specialized for a generic generator. |
| PatternFly component library | Required by OpenShift Console dynamic plugin architecture; provides consistent UX with OpenShift ecosystem. Also works well standalone. |
| Dual deployment target (Console Plugin + Standalone SPA) | Console Plugin provides OpenShift-native experience; Standalone SPA enables demos, local dev, and non-OpenShift deployments without requiring a full cluster. |
| ERD visualization as Phase 2 | Core CRUD + build workflow delivers value immediately. ERD visualization is a nice-to-have that can use a lightweight library (e.g. `reactflow`, `elkjs`) when prioritized. |
| Status polling instead of WebSocket | TRex API is REST-only; no WebSocket/SSE support. Polling at 3s intervals is simple and sufficient for build status monitoring. |
| Project-scoped navigation via query parameters | Matches the flat-route + query parameter convention used by the REST API (APP-001). No nested routes needed. |
| Constrained dropdowns for enum fields | Prevents invalid values at the UI level before the API rejects them. Better UX than free-text with 400 error feedback. |
